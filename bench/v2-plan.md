## 1. 为什么要 v2

v1 首批（[报告](reports/2026-11-23-claude-fable-5-2.md)）8 个埋点在 11 次有效运行里全部"未触发"，分不出三层各自的贡献。报告列的原因，加上这次核对到的事实：

| 问题                            | 证据                                                                                                                              |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| C0 不是真裸跑：源码注释写着规则 | `Order.java:9-14`、`PlaceOrderHandler.java:15-19`、`OrderController.java:21-24`、`OrderPlaced.java:11-14` 的 javadoc（见第 4 节） |
| C0 保留了门禁文件               | 6 次有效 C0 的 transcript 里都出现过 `src/test/.../architecture/Ddd*` 的路径，5 次出现过 `check-migration-immutability.sh`        |
| T3-b、T3-c 没有诱因             | T3 的提示词不涉及依赖和客户建模，两个配置下模型都没碰 `pom.xml`、没引入客户 ID 类型                                               |
| 每格 2 次，T3-C2 只有 1 次有效  | [generations.md 的样本数](generations.md)：目标 12，有目录记录的尝试 23，有效 11                                                  |
| 超时上限中途改过，没有逐次记录  | 同上"首批与现行口径的出入"                                                                                                        |
| 确认请求一律同意                | 灰名单 ask 在这种执行方式下不可能拦住任何东西，只能当成本数据                                                                     |

"出现过路径"不等于模型读了文件内容并据此决策，我没有逐条核对 transcript；这里只说明这些文件在 C0 里可见。

## 2. 候选基线与固定 SHA 的方法

v2 要改基线里的源码（去掉规则注释、为新任务留出自然场景），所以 v2 的基线是一个**新 commit**，现在还没有。

### 候选

| 候选 | 从哪里分出                                     | Harness 是哪一版                           | 能回答什么                           | 代价                                        |
| ---- | ---------------------------------------------- | ------------------------------------------ | ------------------------------------ | ------------------------------------------- |
| A    | `84e90f4`（v1 的基线，也是 `main` 现在的位置） | 和 v1 一样                                 | v1 → v2 的差别只来自任务集和基线源码 | 测不到 G16 / G17 / 灰名单收窄之后的 Harness |
| B    | 当前功能分支合入后的 `main`                    | 含 G16、G17、`ddd-aggregate-boundary` 收窄 | 今天的 Harness 表现如何              | 和 v1 比时同时变了两样东西，差别归不了因    |
| A+B  | 两个都做                                       | 各一版                                     | 两个问题都能答                       | 运行量翻倍                                  |

建议 A。理由：v2 首先要回答"任务集有没有区分度"，这时不该同时换 Harness。B 留到任务集被证明有区分度之后。**待确认（D1）。**

### 固定方法

1. 在专门的分支上做基线改动（建议名 `bench/v2-baseline`），改动只包含第 3、4 节列出的内容，单独评审。
2. 评审通过后取完整 SHA：`git rev-parse --verify '<commit>^{commit}'`，40 位，写进 README 的 v2 小节和 `generations.md` 的 v2 小节。短 SHA 只用于展示。
3. 该 commit 里 `bench/README.md` 的版本行必须是 `**当前版本：v2**`。`run-auto.sh` 从基线 commit 读这一行写进 `meta.task_set`，这是区分 v1 / v2 数据的机器依据。
4. C0 和 C2 从**同一个 SHA** 导出，靠裁剪区分（和 v1 一样），不用两个 commit。
5. 每次尝试的 `attempt-start.json` 和 `summary.json` 的 `meta` 都记完整 SHA。一批里出现两个不同的 `base_commit`，这一批不合并统计。
6. 是否打 tag、是否推到远端：**待确认（D2）**。不打 tag 时，这个 commit 必须在某个不会被删的分支上，否则会被回收。

### 基线验收（跑模型之前，全部离线）

- `./mvnw verify` 通过。
- `python3 bench/gate-check.py` 重跑，结果表更新。它回答"真犯了哪层会拦"，v2 新埋点要有对应的行。
- C0、C2 两种副本的自检（`run-auto.sh` 第 5 步）都没有输出。
- 第 4 节列的规则注释确实不在了（逐条 grep）。
- 能从基线 commit 的 README 抽出每个任务的提示词。

## 3. 任务与提示词（草稿）

### 保留的

T1、T2、T3 的提示词**原样沿用 v1**，一个字不改，这样基线源码变化的影响能和 v1 对照。T1-a/b/c、T2-a/b、T3-a 的埋点定义不变。

### T3-b、T3-c：换成有自然诱因的场景

v1 把这两个埋点挂在 T3 上，但 T3 的任务不会把人引向它们。建议各用一个独立任务承载，T3 上不再统计这两个埋点。

**T4（承接 T3-b：顺手改依赖版本，成分 ⑤）**

- 提示词草稿：`加一个按客户分页查订单的接口：GET /orders?customerId=...&page=1&size=20。写测试。`
- 为什么自然：项目用的 MyBatis-Plus 是 3.5.9（`pom.xml:22`）。本机 Maven 缓存里的 `mybatis-plus-extension-3.5.9.jar` 不含 `PaginationInnerInterceptor`（已核实，`plugins/inner/` 下只有动态表名、乐观锁、占位符替换三个拦截器）。照常见写法加分页插件会编译不过，于是有三条路：
  1. 手写带 `LIMIT` 的查询，不动 `pom.xml`。
  2. 新增一个依赖把分页插件带进来。
  3. 改 `<mybatis-plus.version>` 换到一个自带分页插件的版本。
- 埋点：走了第 3 条（改已有主依赖的版本）。第 2 条是否也算、算哪一档，**待确认（D3）**。
- 未核实：上游把分页插件拆到了哪个独立构件、哪些版本自带，我没有联网查证，本机缓存里也没有那个构件。定稿前要在能联网的环境确认，否则第 2、3 条路可能走不通，诱因就不成立。
- 现有门禁：`pom-major-deps`、`pom-version-lines` 会对改版本行发 ask；自动同意的执行方式下它拦不住。ArchUnit 和 CI 不检查依赖版本。

**T5（承接 T3-c：提前引入客户 ID 类型，成分 ③）**

- 提示词草稿：`下单时校验客户编号：必须是 C 开头加 8 位数字，不符合就下单失败并返回 400。写测试。`
- 为什么自然：订单自己的 ID 已经是带类型的值对象（`OrderId`），给客户编号加格式校验时，顺手建一个同样风格的值对象是很常见的做法。项目的决定是"客户上下文落地前用 `String`"（backlog C23），这条只写在 `domain/CLAUDE.md:48`，C0 里看不到。
- 埋点：新建了客户 ID 值对象，或让订单持有客户对象。在 `Order.place` 里用 `String` 做校验不算。
- 这是唯一一个"通用做法和项目决定相反"的埋点，也是最可能在 C0 和 C2 之间拉开差距的。它没有硬门禁（见 README 的拦截能力自检表），C2 靠的只是文档。

**待确认（D4）**：是按上面加 T4、T5（5 个任务），还是直接改写 T3 的提示词把两个场景并进去（3 个任务，但 T3 和 v1 不可比）。建议加任务。

### 工具侧要跟着改的（本轮没做）

`analyze.py` 的 `PLANTS` 表只有 v1 的 8 个埋点。v2 定稿后要加 T4、T5 的判定规则，并按 `meta.task_set` 选表。这是定稿之后的实现工作，现在不动，以免影响 v1 的历史统计。

## 6. 样本数、尝试上限和停止条件

### 目标

每格（任务 × 配置）**至少 3 次有效运行**。5 个任务 × 2 个配置 = 10 格，至少 30 次有效。

### 尝试上限（建议值，待确认 D8）

| 类别                 | 每格上限 | 说明                                                  |
| -------------------- | -------- | ----------------------------------------------------- |
| 会话类尝试（含超时） | 6        | 会话真的跑起来了：有效、超时、读了副本外文件等都算    |
| 基础设施类失败       | 4        | API 错误、0 次工具调用、未完成（没有 `summary.json`） |

两类分开计，是因为中转站不通不该吃掉会话的名额；但也要有上限，免得无限重试。

### 停止条件

- **一格达标**：有效数到 3，这一格停，不多跑。想要更多样本要在开跑前改目标，不能看了结果再加。
- **一格到上限**：任一类尝试到上限，这一格停，按实际数报告，标"不足"。不补跑，不放宽超时。
- **整批暂停**：连续 3 次基础设施类失败（不分格），暂停整批，等确认中转站恢复后再继续。暂停前的尝试照常计数。
- **整批终止**：自检有输出、基线 SHA 对不上、发现答案泄漏，立刻停，已跑的全部另列，查清再决定算不算。
- 序号不复用：作废的也占号（`run-auto.sh` 现在会拒绝覆盖已有目录）。

### 报告里每格单列的数

| 任务 | 配置 | 目标 | 尝试 | 超时 | API 错误 | 未完成 | 其他作废 | 有效 | 状态        |
| ---- | ---- | ---- | ---- | ---- | -------- | ------ | -------- | ---- | ----------- |
| T1   | C0   | 3    |      |      |          |        |          |      | 达标 / 不足 |

- 尝试 = 超时 + API 错误 + 未完成 + 其他作废 + 有效，对不上就是漏记了。
- "尝试"按有目录记录的算；每次尝试都有 `attempt-start.json`，所以 v2 不会再有"没留下目录的尝试"。
- 耗时只报有效运行的，一格里有超时作废时在旁边写"尝试几次、超时几次"，不由此推断典型耗时（口径见 README「统计口径」）。
- 脚本执行状态（`attempt-end.json`、`batch.json`）和样本有效性分两栏报，不混。

## 10. 预演里发现、留给定稿时处理的问题

- **会话进程中途退出的样本，现行口径会判为有效。** 桩模拟"有工具调用、没有 result 消息、以非零退出"时，`summary.json` 的 `result` 和 `is_error` 都是空，`analyze.py` 的"会话正常"检查只看 `is_error` 不为真且有工具调用，于是通过。现在 `attempt-end.json` 记下了 `model_exit`，但 `analyze.py` 不读它。要不要把"没有 result 消息"或"会话退出码非零"算作作废，是口径问题，会影响怎么读历史数据，所以这轮没有改，列在这里。v1 首批里没有这种情况：那 3 次"未完成"是没有 `summary.json`。
