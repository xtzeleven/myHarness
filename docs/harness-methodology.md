# 给 AI 协作建 Harness：一套可迁移的方法论

**Status**: Shareable（面向外部读者，可脱离本项目语境阅读）
**Date**: 2026-07-28
**Audience**: 想系统性约束 LLM 做工程、又不想被一堆零散 tips 淹没的人

> **本文是什么**：从 [myHarness](../README.md) 项目里提炼出的、**与具体工具无关**的方法论——如何给"AI 辅助工程"这件事建立系统性的防御纵深。
>
> **本文不是什么**：不是 Claude Code / Cursor / Copilot 的配置教程。具体实现（hook 脚本、CI job、agent 文件）只作举例；主体是一套即使换工具、换语言也成立的**思维框架 + 设计原则**。
>
> **一句话**：给 AI 协作建 Harness，本质是回答两个问题——"防御够不够深"和"机制建得全不全"。前者靠**三层视角**，后者靠**六维度视角**，两套交叉扫描才不漏。落地时靠三个原则托底：**灰名单、单一真源+指针、机制化优先**。

---

## 0. 为什么需要"Harness"这个词

"Harness" 原指给马套的挽具——不是笼子（不限制去哪），而是**约束发力方向、防止失控**的装置。

用在 AI 协作上，它精准描述了我们真正想要的东西：**不是限制 LLM 能做什么，而是约束它怎么做、在哪些地方必须停下来问人**。

大多数团队给 AI 协作加约束的方式是**零散的**：

- 一份越写越长的 `AI 使用规范.md`（没人从头读到尾）
- 几条 pre-commit hook（能被 `--no-verify` 绕过）
- code review 时靠人肉盯（AI 生成量一大就盯不过来）

这些都是**单点防御**。单点的问题不是"没用"，而是**你不知道自己漏了什么**——因为没有一个框架告诉你"防御应该覆盖哪些面"。

Harness 方法论的第一价值，就是提供这个"应该覆盖哪些面"的坐标系。

---

## 1. 核心框架：双坐标审视

给 AI 协作建约束，有两个**正交**的问题要回答。它们是两条独立的轴，必须同时扫描。

### 轴一：三层视角 —— "错误被拦在哪个时间点"（防御纵深）

按 LLM 行动的**时间线**切分，一个错误可以在三个时点被拦下：

| 层         | 时点            | 拦什么                           | 典型载体                             |
| ---------- | --------------- | -------------------------------- | ------------------------------------ |
| **约束层** | 行动**之前**    | 让错误的操作"根本想不到要做"     | 注入给模型的规则文档、行动前的硬拦截 |
| **反馈层** | 行动**之中/后** | 让错误"做出来立刻被纠"           | 保存后自动格式化、子任务专项审查     |
| **门禁层** | 提交**之后**    | 让错误"绕过了前两层也合不进主干" | CI 检查、合并保护、不可绕过的测试    |

**为什么三层缺一不可**：每层都会漏。

- 只有约束层：模型可能忽略注入的规则（软约束不强制）
- 只有反馈层：反馈是"事后提醒"，破坏性操作已经发生
- 只有门禁层：反馈周期太长，错误要到 CI 才暴露，本地体验差

三层叠加形成**纵深**——一个错误要三道都穿过才能落地。这是 Harness 相对"单点防御"的第一个质变。

> **关键洞察**：约束层拦不住的，反馈层纠；反馈层漏掉的，门禁层堵。**不要指望任何单层做到 100%**，而要让三层的漏网之处不重叠。

### 轴二：六维度视角 —— "机制类型建得全不全"（覆盖广度）

三层回答"防御够不够深"，但答不了"我是不是有一整类机制压根没建"。这就要换一套按**机制类型**切分的坐标：

| 维度                     | 管什么                               | 没有它会怎样                                 |
| ------------------------ | ------------------------------------ | -------------------------------------------- |
| **Loop（循环）**         | 任务如何分派、重试、升级、降级       | 子任务调度全靠临场即兴，质量随会话漂移       |
| **Context（上下文）**    | 每次注入给模型什么、成本多少         | 注入膨胀，关键规则被淹没或超预算被截断       |
| **Tools（工具）**        | 能调哪些工具、版本锁定、失败降级     | 工具版本本地与 CI 不一致；工具挂了无退路     |
| **Permission（权限门）** | 哪些操作需人工确认、哪些直接拒绝     | 危险操作和日常操作一视同仁，要么全拦要么全放 |
| **Memory（记忆）**       | 跨会话沉淀什么（偏好、踩坑、决策）   | 每个新会话重复踩同样的坑                     |
| **Policy（策略）**       | 机制之间的元规则（何时升级/降级/停） | 有机制但没有"何时用哪个"的规则，各机制打架   |

**为什么单靠三层会漏掉整个维度**：三层是"时间轴"，看不见"机制类型"这个维度。你可能沿三层反复加 hook（都落在反馈层），却从没意识到 **Memory 维度完全空白**——每个新会话都在重新踩三个月前踩过的坑。这种缺失，只有六维度这条轴扫得出来。

### 两轴如何交叉使用

把两轴画成矩阵，每个格子是一个"该不该有防御"的检查点：

```
              约束层        反馈层         门禁层
Loop          任务分派规则   重试/升级机制   —
Context       注入什么       —              注入成本 CI 基线
Tools         版本锁         失败降级链      工具漂移检查
Permission    黑/灰名单      —              合并前权限审查
Memory        —              踩坑自动召回    —
Policy        选择规则       升级/降级触发   审计日志
```

**用法**：拿这个矩阵逐格自问"这里有没有防御？需不需要？"。空格不一定都要填满（有些格子对你的场景 N/A），但**每个空格都应该是"想过之后决定不填"，而不是"压根没想到"**。

这就是双坐标的全部价值：**把"我可能漏了什么"从盲区变成一张可以逐格扫描的表**。

## 2. 三个可迁移的设计原则

框架告诉你"该在哪建防御"，原则告诉你"每处防御该怎么建"。这三条是从大量试错里收敛出来的，换工具、换语言都成立。

### 原则一：灰名单 —— 在"允许"和"拒绝"之间加一个"问人"

**问题**：大多数权限设计是二元的——允许，或拒绝。但 AI 协作里的大量操作是**第三种**：危险，但有时完全合理。

- 改核心领域模型的边界：可能是必要重构，也可能是模型走偏
- 升级主框架依赖版本：可能是安全补丁，也可能引入不兼容
- 删除文件、重写配置：可能是清理，也可能是误删

二元设计对这些操作只能二选一：**全拦**（挡住合理需求，逼人绕过）或**全放**（放行危险操作）。两个都错。

**解法**：引入三态。

| 名单       | 行为                             | 适用                                               |
| ---------- | -------------------------------- | -------------------------------------------------- |
| **黑名单** | 直接拒绝                         | 无论如何都不该做（删根目录、强推主干、写密钥文件） |
| **灰名单** | **暂停，要求人明确授权后才继续** | 危险但可能合理（改核心边界、升主依赖）             |
| **白名单** | 直接放行                         | 日常安全操作                                       |

**灰名单是这套设计的灵魂**。它承认了一个 AI 协作的本质事实：**很多决策不是对错问题，而是"需要一个人看一眼"的问题**。它把人的注意力**精确投放**到真正需要判断的地方，而不是让人淹没在"确认所有操作"或"什么都不管"两个极端里。

> **迁移提示**：不管你用什么工具，问自己——"哪些操作我希望 AI 停下来问我，而不是自己决定，也不是被完全禁止？"这批操作就是你的灰名单。把它显式列出来，比任何笼统的"AI 要谨慎"都有用。

### 原则二：单一真源 + 指针 —— 不消除重复，而是给重复定权威

**问题**：AI 协作项目的头号杀手是**文档漂移**——同一个信息（当前进度、某个配置、某条规则）散落在多处，改了 A 忘了改 B，模型读到过期的 B 就跟着错。

**反直觉的解法**：不要试图消除所有重复。信息天然会在多处出现（README 要提、CHANGELOG 要记、规则文档要引用）。硬压成"零重复"会让文档失去可读性。

**正确姿势**：为每一类信息**指定唯一权威源**，其余所有位置降级为**指向权威源的指针**。

```
进度信息   → 权威源：某个进度表      其余位置：写"以 XX 为准"
模型选择   → 权威源：某个策略表      其余位置：一行注释 + 指针
规则数据   → 权威源：某个数据文件    其余位置：加载它，不复述
```

**为什么这个比"零重复"强**：

- 保留了可读性（每处该提的还提，只是提的是指针不是内容）
- 消除了漂移（内容只有一处能改，其余无内容可漂）
- 可机器校验（可以写脚本检查"所有指针指向的源真的存在且一致"）

**进阶：把真源变成机器可读的单点**。最高级的形态是让权威源不只是"约定上唯一"，而是**技术上唯一**——比如一份结构化清单（YAML/JSON），文档表格、CI 检查、运行时逻辑全部**从它派生**，任何一处不同步就 CI 报错。这样"单一真源"就从纪律变成了机制。

> **迁移提示**：列出你项目里"改一处要同步好几处"的信息（进度、配置、清单）。每一类，指定一个权威源，把其余变成指针。如果同步点多到靠人记不住——那就是该写个校验脚本的信号。

### 原则三：机制化优先 —— 能拦住的，就不要只写下来

**问题**：规则文档里写"应该做 X / 不要做 Y"，是**软约束**。软约束依赖模型（和人）自觉遵守，而 AI 协作的规模一大，自觉就靠不住。

**核心区分**：

| 形态       | 保障强度     | 例子                                           |
| ---------- | ------------ | ---------------------------------------------- |
| **写下来** | 劝告，可无视 | 文档里写"核心层不要依赖框架"                   |
| **拦得住** | 机制，绕不过 | CI 里用脚本扫描，一旦核心层出现框架依赖就 fail |

**"写下来"和"拦得住"是两个量级的保障**。前者是"我告诉过你了"，后者是"你做不到"。

**方法论**：把每条软约定过一遍这个问题——"**它能不能变成一段代码/一个检查？**"

- 能 → 就该机制化（变成 CI 门禁、变成 hook 拦截、变成校验脚本）
- 不能（判断太主观，如"命名要清晰"）→ 才留在文档里当劝告，并接受它的软性

这个筛选会让你的规则文档**越来越短**（可机制化的都搬走了），而防护**越来越硬**（搬走的都变成了绕不过的门禁）。

> **迁移提示**：翻你的"AI 使用规范"，逐条问"这条能不能写成一个检查？"。你会发现相当一部分能——那些就不该待在文档里等人遵守，而该变成 CI 里一行 `grep` 或一个测试。

## 3. 把框架变成自查清单

方法论要能落地，得能自查。把前两节压缩成一张可执行的 checklist：

**第一遍：三层纵深够不够**

- [ ] 有没有"行动前"的约束（注入模型的规则 + 危险操作的硬拦截）？
- [ ] 有没有"行动中/后"的反馈（自动修正 + 专项审查）？
- [ ] 有没有"提交后"的门禁（CI + 合并保护 + 不可绕过的测试）？
- [ ] 三层的漏网之处是否**不重叠**（不是三层都在防同一件事）？

**第二遍：六维度覆盖全不全**

- [ ] Loop：任务分派/重试/升级有没有规则，还是全靠临场？
- [ ] Context：每次注入什么、成本多少，审计过吗？
- [ ] Tools：版本锁了吗？工具挂了有降级路径吗？
- [ ] Permission：有没有灰名单（不只是黑白）？
- [ ] Memory：踩过的坑会不会在新会话自动召回？
- [ ] Policy：机制之间"何时用哪个"有没有元规则？

**第三遍：三原则贯彻了没**

- [ ] 危险但合理的操作，走的是灰名单（问人）而非全拦/全放？
- [ ] 每类易漂移信息，有唯一真源 + 其余是指针？
- [ ] 可机制化的约定，真的机制化了，还是停在文档里？

任何一项答"没有/没想过"，就是一个待补的洞。

## 4. 边界：什么时候**不该**用这套东西

方法论最容易被滥用的方式，是**不分场景地全套照搬**。诚实说清它的适用边界：

**投入与产出要匹配**。这套 Harness 有真实的建设和维护成本（写 hook、配 CI、维护真源、写校验脚本）。它的收益随**两个因素**放大：

- **AI 生成代码的比例**：AI 写得越多，人肉 review 越顾不过来，机制化防护的杠杆越大
- **项目的存续时间**：一次性脚本不值得建 Harness；长期演进的项目才摊得平成本

**因此**：

| 场景                            | 建议                                   |
| ------------------------------- | -------------------------------------- |
| 一次性脚本 / demo / 探索性原型  | ❌ 别建，用判断力就行                  |
| 短期项目、AI 参与少             | ⚠️ 只取灰名单 + 一两条关键门禁，别全套 |
| 长期演进、AI 深度参与、多人协作 | ✅ 值得完整建，成本会被反复摊平        |

**还有一个复杂度上限**：机制越多，维护机制本身的成本越高。当你发现"新增一个东西要同步七个地方"时，那不是"该更努力同步"的信号，而是"复杂度逼近上限、该用原则二（真源机器化）收敛"的信号。**Harness 是用来降低协作成本的，如果它自己成了成本，就本末倒置了。**

---

## 5. 一页纸总结

> **给 AI 协作建 Harness = 系统性的防御纵深，不是零散的规则堆叠。**
>
> **两条轴交叉扫描找漏洞**：
>
> - 三层（约束/反馈/门禁）——防御够不够**深**
> - 六维度（Loop/Context/Tools/Permission/Memory/Policy）——机制建得够不够**全**
>
> **三个原则托底**：
>
> - **灰名单**：在"允许/拒绝"之间加"问人"，把人的注意力精投到需要判断处
> - **单一真源 + 指针**：不消除重复，而是给每类信息定唯一权威源，其余降级为指针
> - **机制化优先**：能变成检查的约定，就不要只写在文档里等人自觉
>
> **别忘边界**：投入要匹配 AI 参与度和项目寿命；机制自己成了成本就该收敛。

## 附：本方法论的来源与局限

本文提炼自 [myHarness](../README.md)——一个"用自己定的规则约束开发自己"的自指项目。方法论在该项目自身上跑通了完整闭环（改配置要过自己的 CI、改规则要过自己的门禁）。

**但要诚实标注局限**：截至沉淀本文时，这套方法论的实战验证样本量是 **N=1**（作者完全控制的单一项目）。它证明了"能约束开发 myHarness 自己"，尚未充分验证"能约束一个作者不控制全局、有真实业务压力、多人协作的项目"。**读者迁移时，请把它当作一套经过一手试错但仍需在你的场景里再验证的框架，而非现成结论。**
