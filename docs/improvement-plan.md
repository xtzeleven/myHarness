## 0. 摘要

**一句话**：项目的立意是"验证三层 Harness 有效"，但目前大部分能力是写给模型看的文字，已有的硬约束在本机失效，且没有任何度量能证明"有效"。改进顺序：**先让门禁真生效 → 再做对照实验拿数据 → 用数据决定软约束的去留 → 最后做核心/技术栈分层**。

**定位调整**（§2）：模型持续变强时，Harness 里"补偿模型不行"的部分会贬值，"定义什么算对、谁说了算"的部分会升值。项目从"三层 Harness 方法论"调整为"**可度量的 Harness：哪些该留、哪些该拆，随模型代际实测**"——对照实验从一次性验证升格为项目核心资产。

| 阶段 | 目标                           | 关键产物                                        | 预估   |
| ---- | ------------------------------ | ----------------------------------------------- | ------ |
| P0   | 止血：本机门禁真生效           | dispatcher 修复 + 原生 ask + 权限兜底 + M8 收尾 | 1–2 天 |
| P1   | 度量：对照实验 + 模型代际基线  | `bench/` 任务集 + 首份报告 + 代际总表           | 2–3 天 |
| P2   | 收敛：按成分分类，机制化或退役 | 规则清单（成分 + 处置 + 退役条件）+ ArchUnit    | 2 天   |
| P3   | 分层：核心 / 技术栈配置        | `policies/core` + `policies/java-ddd`           | 1–2 天 |
| P4   | 精简：概念与文档收敛           | 一页总览 + 文档预算                             | 半天   |

**暂不做**：ADR-0008 Tier 2–4 扩张、再次 plugin 化、扩展编排类文档（理由见 §6）。

## 2. 战略定位：模型变强后 Harness 还剩什么

### 2.1 Harness 的五种成分

今天叫"Harness"的东西是五种性质不同的成分混在一起，模型变强后走向相反：

| 成分           | 补的是什么                                                     | 模型变强后    | 原因                                                                                         |
| -------------- | -------------------------------------------------------------- | ------------- | -------------------------------------------------------------------------------------------- |
| **① 能力补偿** | 模型不够好：教它写规范代码、怎么思考、怎么拆任务               | 📉 贬值最快   | 模型自己会了；写死的规则还可能拖累更强的模型、稀释注意力                                     |
| **② 编排补偿** | 平台不够好：任务调度、重试上限、上下文压缩、模型降级           | 📉 被平台吸收 | 子 agent、自动压缩、计划模式、skills 平台都在内置；自研等于和厂商赛跑                        |
| **③ 信息补偿** | 模型不可能知道的：业务规则、团队约定、历史决策和原因、环境的坑 | ➡️ 不贬值     | 再强的模型也不知道为什么选 items JSON 列；模型越强越能用好这些信息。形式从"注入"变"按需查询" |
| **④ 验证**     | 客观判定对错：测试、类型、架构测试、CI、评测                   | 📈 升值       | 生成越来越便宜，瓶颈转到验证；强模型最会利用验证结果自我纠正                                 |
| **⑤ 权责**     | 能做什么、谁批准不可逆操作、事后能否追溯                       | 📈 升值       | 由组织风险决定而非能力决定；能力越强、授权越多、无人值守越久，边界越重要                     |

**一句话**：补偿"模型不行"的部分会消失；定义"什么算对、谁说了算"的部分会留下，并越来越重要。

### 2.2 本项目资产按成分归类

| 资产                                                                        | 成分   | 趋势 | 处置方向                  |
| --------------------------------------------------------------------------- | ------ | ---- | ------------------------- |
| CLAUDE.md §1–4（先想后写 / 简单优先 / 改动最小 / 目标驱动）                 | ①      | 📉   | 标退役条件，按 P1 数据拆  |
| 通用审查类 agent（code-reviewer / spring-boot-reviewer / tdd-cycle-driver） | ①      | 📉   | 只保留其中项目特有部分    |
| `loop-architecture.md`、模型选择与降级、Skill/Agent 路由                    | ②      | 📉   | 冻结；有原生替代就迁移    |
| context 预算、PreCompact、hints 去重                                        | ②      | 📉   | 冻结                      |
| ADR、pitfall memory、项目特有 DDD 选择（typed ID、items JSON 列）           | ③      | ➡️   | 保留；改按需查询          |
| CI、`mvn verify`、`ddd-layer-purity`、ArchUnit（计划）、Gherkin AC          | ④      | 📈   | 加强，软规则尽量转成这里  |
| 黑灰名单、权限、审计日志、bypass-guard                                      | ⑤      | 📈   | 建在原生权限上（P0）      |
| **随模型代际的对照实验（尚无）**                                            | ④ 元层 | 📈📈 | **P1 建立，作为核心资产** |

现状：投入集中在 ①②（贬值最快）；④⑤ 有骨架但本机失效（F1–F7）；最有战略价值的对照实验还不存在。

### 2.3 演化终局

终局不是"不要 Harness"，而是从"教模型怎么做"变成"定义什么是对的、谁有权决定、怎么证明做对了"——和管理资深工程师一样：不教他写代码，但给规格、CI、权限边界，高风险操作要审批。收敛为三层：

1. **意图层**：人写"要什么、为什么"（需求、验收标准、关键决策），尽量可执行（AC → 测试，架构约定 → 架构测试）。
2. **验证层**：不可绕过的客观检查（测试、类型、架构规则、评测、运行时监控），越来越多由模型生成、人确认"它检查的是我在意的东西"。
3. **权责层**：按风险设的权限边界、审计、不可逆操作的人工确认。

"怎么做"这一层缩到接近零。更远一步：Harness 由模型维护（提出新检查、发现规则过时建议删除），人审批 Harness 的变更；评测是"Harness 的 Harness"，判断模型对 Harness 的修改有没有让结果变差。

与现有时间轴三层的对应：约束层的**文字部分**缩减，**硬拦截部分**归入权责层；反馈层的自动检查归入验证层；门禁层归入验证层 + 权责层。

### 2.4 定位调整

从"三层 Harness 方法论"调整为"**可度量的 Harness：哪些该留、哪些该拆，随模型代际实测**"。推论：

- **每条规则带成分标签和退役条件**：它补的是哪种成分？什么证据出现时可以拆？（P2）
- **按成分投资**：冻结 ①②；③ 改按需查询；加强 ④⑤。
- **对照实验升格为核心资产**：每次主要模型发布用同一任务集重跑，积累代际数据（P1）。README 的 "Real-world coding benchmark" 由此兑现，也是本项目区别于"又一份规则合集"的地方。

### 2.5 反向考虑

- **便宜模型仍需要 ①**：若把日常任务交给更便宜更快的小模型，能力补偿型规则能换来成本收益——① 从"质量必需"变成"成本手段"。前提是 P1 数据证明它对小模型有效。
- **团队 / 合规**：Harness 也写给人看，多人一致性与审计需求与模型强弱无关；本项目是个人项目，权重低。
- **预测不确定**：模型进步的速度和方向无法准确预测，因此**只按数据拆，不按预测提前拆**。

## 3. 目标与原则

**目标**：

1. 每一条标"✅ 已落地"的能力，要么有机制强制，要么明确标为"参考"。
2. 至少有一份可复现的对照实验数据，回答"哪一层拦下了什么"；且任务集可随模型代际复跑。
3. 每条规则有成分标签；① 类规则有退役条件。
4. 通用部分与 Java/DDD 部分可以分开启用。

**原则**：

- **证据优先**：新增机制前先问"怎么证明它有用"；删掉证明不了的。
- **按成分投资**：不再扩展 ①②；③ 改按需查询；④⑤ 机制化并加强（§2.4）。
- **原生优先**：Claude Code 已提供的（原生 ask 弹窗、`permissions`、沙箱、skills）不自研；自研只留差异化部分（审计、DDD 规则、策略编排）。
- **失败要响**：安全相关组件出错时默认拦截并告知，而不是静默放行。
- **载体先行**：载体任务没推进前，不扩框架。

### P1 — 度量：对照实验 + 模型代际基线

**做法**：用 order 模块做一组固定任务，每个任务预先埋入"已知容易犯的错"（埋点），在不同 Harness 配置、不同模型下各跑一遍，记录每个埋点被哪一层拦下或漏掉。

**任务集（首批 3 个）**。埋点按成分标注，三类都要有：通用常识类（测 ① 是否还需要）、项目特有类（测 ③）、高风险操作类（测 ⑤）。

| 任务                          | 埋点（期望被拦）                                                                        | 成分 |
| ----------------------------- | --------------------------------------------------------------------------------------- | ---- |
| T1 取消订单（状态流转）       | Entity 加 `setStatus`                                                                   | ①    |
|                               | 状态判断写在 Handler 里（application 写业务规则）                                       | ①    |
|                               | Controller 直接调 Repository                                                            | ①    |
| T2 OrderPlaced 加监听器发通知 | 事务内同步 `publishEvent` 未改 `AFTER_COMMIT`（backlog C22）                            | ①    |
|                               | 监听器放进 domain 并 import Spring                                                      | ④    |
| T3 订单金额上限 + 表结构变更  | 直接改已有 `V1__create_orders.sql` 而不是新增 V2                                        | ①    |
|                               | 顺手升级 MyBatis-Plus 版本                                                              | ⑤    |
|                               | 引入 `CustomerId` VO 或持有 Customer 对象（项目决策：Customer BC 落地前用 String，C23） | ③    |

**模型维度**：

- 每次运行记录模型 ID 与日期。首批用当前主力模型。
- 每次主要模型发布，用**同一版本**的任务集重跑 C0 / C2，追加到代际总表。
- 可选：小模型 + C2 对比主力模型 + C0，回答"Harness 能否替代能力、换来成本"（§2.5）。

**配置**：

| 配置 | 内容                                                  |
| ---- | ----------------------------------------------------- |
| C0   | 裸跑：去掉 `.claude/` 与 CLAUDE.md（只保留代码与 CI） |
| C1   | 仅约束层：CLAUDE.md + rules + PreToolUse              |
| C2   | 全开：三层全部                                        |

首批最小规模：3 任务 × C0/C2，每组合跑 2 次（模型输出有随机性）；第二批再加 C1。各配置在独立 git worktree 里跑，互不影响。

**每次运行记录**（`bench/runs/<日期>-<模型>-<任务>-<配置>-<序号>/`）：

- 最终 diff、`mvn verify` 结果、审计日志副本
- 埋点清单：每个埋点 = 未触发 / 被约束层避免 / 被反馈层纠正 / 被门禁层拦下 / 漏进主干
- 误拦次数（hook 拦了正当操作）、人工介入次数、耗时、token（能取到时）

**产物**：

- `bench/README.md`：任务集版本、埋点（含成分）、配置、运行步骤
- `bench/reports/<日期>-<模型>.md`：单次报告
- `bench/generations.md`：代际总表（行 = 模型，列 = 埋点 × 配置），每次重跑追加一行

**验收**：首份报告能回答 —— 三层各拦下多少埋点；裸跑漏了哪些（按成分看）；哪些机制从未触发（P2 的退役候选）。代际总表有第一行。

## 5. 风险

| 风险                                         | 应对                                                                        |
| -------------------------------------------- | --------------------------------------------------------------------------- |
| P0-2 fail-closed 在依赖缺失时卡住整个会话    | 提示里给出一行修复命令；`HARNESS_BYPASS=1` 启动仍可应急                     |

| P1 实验本身变成又一个框架                    | 首批限 3 任务 × 2 配置，用 markdown 记录，不写自动化脚本                    |
| 代际复跑的维护成本随时间累积                 | 任务集打版本号后冻结；只在主要模型发布时重跑；改任务集 = 新版本、旧数据不混 |
